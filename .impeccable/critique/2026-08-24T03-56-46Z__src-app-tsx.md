## Design Specificity Verdict

Visual language is authored for this product; composition is not; README describes an app that no longer exists.

Derived and auditable: asymmetric 4%/1% page inset honoured rather than tidied (global.css:181); shadow thrown down-and-LEFT because measured; hover convention inverted with reasoning transferred (global.css:9-17); dark theme built from the capture's own footer band. More genuine authorship than almost any app carries.

But strip the copper band and all-caps labels and what remains is the universal asset-manager skeleton. The one product-native component is PaletteStrip (sqrt(share)*4 weighting) — 20px tall, below the fold, and its swatches are dead buttons at BOTH call sites.

Deterministic scan: CLI over markup 0 findings exit 0, validated via positive control. Coverage limit found: regex engine reads CSS syntax not JSX style objects, so 2341 lines of CSS fell outside a markup-only scan. Supplementary CSS pass surfaced 2 findings, 1 real (side-tab toast border). In-browser across 5 views: text-overflow x3 (414-449px of the Layout field hidden), all-caps-body, cream-palette, border-accent-on-rounded x3 (deliberate keycap idiom), flat-type-hierarchy at mobile. False positive: clipped-overflow-container x3 flags .visually-hidden. Mis-attribution: layout-transition is the progress bar (global.css:1379). Runtime completely clean — zero errors across all exercised flows.

## Priority Issues

### [P0] `CLEAR ALL` in the filter bar deletes the entire catalog
App.tsx:986 renders btn-ghost btn-danger onClick={wipeCatalog} as last item in filter toolbar, after "{visible.length} shown". wipeCatalog (:724) calls clearCatalog(). EmptyState.tsx:25 labels the SAFE action "Clear filters", teaching that clear = filters. .btn-danger has only a :hover rule (global.css:521) so it doesn't look destructive at rest. With auto-sync on, deletion propagates to Drive in 2.5s as tombstones designed to stick. No undo, no trash.
Fix: remove from filter bar; move to sync panel danger zone; rename "Delete entire catalog"; give .btn-danger a resting state; replace confirm() with typed-word dialog.
Command: /impeccable harden

### [P1] No undo on any destructive action; touch shows a live delete on every card
Three delete paths (App.tsx:495, :686, :725) plus wipe-on-sign-out, none reversible. .card-hover-actions computes opacity:1 under (hover:none) — every card carries a permanently visible 35px trash ~8px from copy, on the screenshot. Local-first = no server recycle bin.
Fix: soft-delete + 30-day window + Undo in toast (10s) + Recently deleted section; then drop confirm() on single deletes.
Command: /impeccable harden

### [P1] Sync panel declares aria-modal but its focus trap has never run
SyncPanel.tsx:67 calls useOverlay, then :69 is `if (!settings) return null` with settings initialised null and filled async. At mount the div was never rendered, overlayRef.current is null, effect deps [onClose, ref] both stable (overlay.ts:150) so the null is captured permanently. node?.focus() no-ops; Tab handler short-circuits at overlay.ts:118 forever. Escape still works (checked at :119 before the !node guard) so it fails silently. Measured: 20 consecutive Tabs landed on catalog controls behind the panel; 25/25 stops escaped. aria-modal hides background from AT, so a screen-reader user tabs into content their AT says doesn't exist. Drive setup is keyboard-unreachable. 1 of 2 useOverlay call sites broken by statement ordering. WCAG 2.4.3, 4.1.2.
Fix: move `if (!settings) return null` above the useOverlay call.
Command: /impeccable harden

### [P1] One image freezes the UI 1.8s; import is near-silent
analyzeBlob (analyze.ts:23-60) synchronous; no Worker/requestIdleCallback in src/. Measured on 2880x1800 PNG: 1 long task 1801ms, TBT 1751ms, worst frame 1808ms (~108 dropped frames). 48 images = 35s with zero cards for first ~24s, screen reading "YOUR CATALOG IS EMPTY". report.failed carries {name,reason} and discards both.
Fix: analyzeBlob into a Web Worker (touches no DOM; ImageBitmap + typed arrays are transferable); skeleton tiles; "Analysing 12 of 25" in masthead; persistent failure banner with filenames.
Command: /impeccable optimize, then /impeccable onboard

### [P1] Measured values and empty placeholders are indistinguishable
.field input::placeholder is --text-faint #6b594e (4.84:1) vs value #322d2f (9.86:1); same size/weight/family. TYPE SCALE shows placeholder "32px/600/1.2/-0.02em" beside measured "~54px/regular (7px stem)" with no perceptual class difference. Dark mode worse. This is the product's core honesty claim rendered invisibly; users will believe seven type steps are recorded and be surprised when the export drops five.
Fix: make empty structurally different (dashed border + hint icon); measured/estimated tick; "4 of 9 recorded" per section header. MEASURED CONTRAST already proves the pattern.
Command: /impeccable clarify

### [P1] Error and success toasts are visually indistinguishable
Toast.tsx:47 renders {toast.message} only — no icon, no prefix — while global.css:1408-1421 distinguishes info/success/error purely by border-left-color. In this palette --success is #5c3517 (brown) / #c5b4a1 (tan) and --danger is #322d2f (the body text colour) / #fbf7ec (the page cream). No red, no green, because the 8 tokens are measured from a screenshot that contained neither. Sole severity cue is a 3px border that is near-black ink in light and near-white in dark. Compounding: role="status" aria-live="polite" so errors announce non-assertively; error toasts auto-expire 6s with no dismiss or history; MAX_VISIBLE=3 drops older toasts so import failures scroll away. WCAG 1.4.1 (A). Distinct from contrast, which measures flawless — these colours are readable, just not distinguishable from each other. This is where the "only measured tokens" conceit costs the user.
Fix: icon + text prefix per kind; errors to role="alert"/assertive; error toasts persist until dismissed. Either admit two non-measured semantic tokens or carry severity by glyph and word.
Command: /impeccable clarify, then /impeccable harden

### [P1] README documents a design system two generations stale
Found independently by all three tracks. README.md:57-66 documents "Vermilion Frontispiece"; global.css:2 declares COPPER PANORAMA; App.tsx:127 names a third vintage "Flint Panorama". Five of six rows wrong: palette (all 8 tokens), radius (8px vs 24px), faces (Young Serif + Hanken Grotesk vs Public Sans only — type.css says the serif was deleted), type scale (12/14/16/20/24/32 vs 12/14/17/24/34/clamp), page inset (5%/5% vs 4%/1%). Only the spacing row survives. Prose stale too. Residue confirms migration: global.css:1459 hard-codes #2b1b21, a token from the superseded palette, and it is the only hard-coded colour in 2341 lines.
Fix: regenerate the Look and feel table from the shipped :root; swap #2b1b21 to var(--chrome).
Command: /impeccable document

## What's Working

1. The design system is falsifiable — global.css:1-230 is an argument, not a token file. Every visual decision can be checked against a measurement.
2. Uniform tiles with footers that read as a table down the page (CatalogGrid.tsx:3-17 documents replacing masonry precisely so footers could be scanned across). Correct, unglamorous, mode-appropriate.
3. The detail drawer is a textbook modal (focus to container deliberately not first input, Tab wrapping both ends, Escape, focus restored to the originating card; 0/40 stops escaped). Alongside: 0 failing contrast pairs both themes, memo + 25 memo hooks, median frame 16.7ms at 48 cards, zero will-change/backdrop-filter/blur, 97.85 kB gzipped on two dependencies.

## Questions to Consider

1. If the footer is the point of the app, why is the thumbnail the biggest thing on the card?
2. The app measures contrast, radius, elevation and type ratios, then prints them into text inputs. What would the drawer look like if every measured value rendered as itself?
3. Twenty-four sort-and-group options is the interface admitting it does not know what a catalog is for. Which three of each would you ship?
4. What if the app's own skin were a record in the catalog — openable, re-analysable, CSS-exportable? The conceit could not drift, because pixels and documentation would be the same object.
